# 性能基线与目标

对应审计项 G-05（核心接口的响应时间与并发目标）。本文给出**目标值**与**实测基线**；`apps/server/tests/perf-guard.test.ts` 以约 10 倍余量守住数量级，避免无意引入全表扫描或 N+1 查询。重新测量：`npm run bench`（`BENCH_ACTIONS` 可调行动次数）。

## 目标（单机自用）
| 项 | 目标 |
|---|---|
| 固定行动、突破、放置修炼结算（p95） | ≤ 50 ms |
| 读接口：状态、日志、背包（p95） | ≤ 20 ms |
| 启动（打开 + 迁移 + 读取） | ≤ 1 s |
| 每个行动的存档增长 | ≤ 5 KB |
| 并发 | 单进程串行处理（SQLite 同步事务）；50 个并发提交应在 1 s 内完成 |

## 实测基线（以下由 `npm run bench` 生成）
### 测量日期 2026-10-23

环境：Node v22.22.0，Intel(R) Xeon(R) Processor @ 2.10GHz × 4，linux；文件数据库（WAL）；行动 1000 次。

## 规则函数（纯计算，无 IO）
| 函数 | 单次耗时（µs） | 每秒次数 |
|---|---|---|
| resolveFixedAction（修炼） | 0.399 | 2,507,939 |
| resolveBreakthrough | 0.188 | 5,313,338 |
| settleIdleCultivation（600 片） | 0.358 | 2,794,246 |

## 接口延迟（Fastify inject，含校验、事务、审计与日志写入；单位 ms）
| 接口 | 平均 | p50 | p95 | p99 | 最大 |
|---|---|---|---|---|---|
| POST /actions 固定行动（1000 次） | 4.27 | 3.65 | 7.01 | 10.8 | 24.5 |
| POST /actions 幂等回放 | 0.612 | 0.573 | 0.710 | 3.33 | 4.08 |
| POST /actions 突破（被拒绝） | 1.65 | 1.40 | 3.22 | 5.22 | 16.0 |
| POST /cultivation/settle | 2.99 | 2.67 | 4.92 | 7.08 | 9.07 |
| GET /player/state | 0.588 | 0.552 | 0.746 | 2.18 | 2.56 |
| GET /log?limit=100（库内 1097 条审计） | 1.58 | 1.37 | 2.40 | 3.53 | 3.81 |
| GET /player/inventory | 0.213 | 0.180 | 0.389 | 0.611 | 1.74 |

并发：同进程 50 个并发行动提交共耗时 227.0 ms（约 220 次/秒）。

## 存档
- 1051 个行动、1097 条审计事件后，数据库文件 2676 KB；每个行动平均增长约 2736 字节（含行动记录、审计事件与日志）。
- 启动（打开 + 迁移 + 读取）：空库 29.4 ms；含 1097 条审计的存档 4.70 ms。

## 结论与注意
- 全部指标远优于目标（行动 p95 ≈ 7 ms，读 p95 ≈ 3 ms，启动 ≈ 32 ms，每行动约 2.7 KB）。
- 行动耗时主要是 SQLite 的 WAL 提交；幂等回放与读接口为亚毫秒到毫秒级。
- 存档按每个行动约 2.7 KB 增长（行动记录含完整角色快照，约占一半）。按每天 1000 次行动计，一年约 1 GB——单机足够，但长期游玩建议在 S6 前评估审计与日志的归档/清理（见 K-16）。
- 此基线为 `inject` 直连，未含 HTTP 与浏览器开销；本机访问时额外开销通常在毫秒级。
- 数据来自 4 核云端容器，个人电脑通常更快；若需对比，请在同一台机器上重复运行。
