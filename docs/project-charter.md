# 1. 项目摘要

《江湖志》是一款以文字交互为核心、结合放置成长与 AI 动态叙事的网页武侠游戏。玩家通过修炼、探索、结交人物、完成任务及自由描述行动参与江湖；程序维护可验证的游戏规则与持久状态，AI 负责理解意图、生成行动建议、演绎人物和呈现结果。

核心原则：规则确定性、剧情生成性、世界持续性、行动开放性、状态可追溯性。

# 2. 产品目标与成功标准

- 提供可持续的角色成长循环：修炼、资源获取、武学提升、境界突破。

- 支持固定选项与自然语言自由输入，两种交互进入统一的行动处理流程。

- NPC 能依据身份、目标、关系和已记录的历史事件持续反应。

- 玩家离线期间可按规则结算修炼收益，并推进符合条件的世界事件。

- 关键状态变更可追踪，重要操作具备幂等保护和异常恢复路径。

- 首期交付可通过浏览器访问的可玩版本，而不是仅有静态界面或剧情演示。

# 3. 范围与边界

## 3.1 首期范围

- 单玩家角色、基础属性、境界、武学、体力、银两和背包。

- 修炼放置、在线与离线收益、服务端时间结算。

- 固定选项、自由输入、AI 意图解析、程序规则判定及叙事反馈。

- 少量地点、初始 NPC、关系记忆、简单任务链和世界事件。

- 持久化存档、行动日志、错误日志、成本统计和基础审计。

## 3.2 暂不纳入首期范围

- 多人在线、玩家自由交易、拍卖行和跨服系统。

- 大规模实时战争、复杂经济模拟和无限地图自动生成。

- 完整商业化、排行榜、公会系统及高并发运营能力。

- 每秒调用 AI 推进世界；挂机与常规结算必须由程序完成。

# 4. 目标用户与核心体验

目标用户偏好文字冒险、武侠世界观、长期养成、策略选择及由自身行为产生的非固定剧情。核心体验不是“AI 能写故事”，而是“玩家行动能够改变一个可信、持续演化的江湖”。

# 5. 核心玩法循环

1.  修炼或执行日常行动，积累属性、资源和信息。

2.  遇到人物、任务、环境或世界事件。

3.  选择预设选项，或输入自由行动目标。

4.  AI 将意图转为结构化行动方案；服务端检查条件并计算结果。

5.  服务端提交状态变更，AI 根据已确认结果生成叙事反馈。

6.  记录历史、更新 NPC 记忆与后续事件，并保存存档。

# 6. 技术路线

| **层级**   | **基线方案**                             | **原则**                             |
|------------|------------------------------------------|--------------------------------------|
| 前端       | Vue 3 + TypeScript + Vite + Tailwind CSS | 响应式界面；业务状态以服务端为准     |
| 后端       | Node.js + TypeScript + Fastify           | 模块化单体；集中处理权限与规则       |
| 数据       | PostgreSQL + Drizzle ORM                 | 事务、迁移、约束与备份               |
| 校验与测试 | Zod + Vitest                             | 边界数据先校验；规则可自动测试       |
| AI         | 服务端模型适配层                         | 可替换供应商；输出结构化且不直接改库 |
| 工程       | Git、环境变量、CI 检查                   | 可复现构建、可审查变更               |

# 7. 阶段规划

| **阶段**      | **目标**                         | **主要出口条件**             |
|---------------|----------------------------------|------------------------------|
| S1 原型       | 项目骨架、主界面、角色与固定行动 | 可启动、可操作、基础存档有效 |
| S2 规则与时间 | 规则引擎、离线收益、幂等与审计   | 结算可复现，无重复奖励       |
| S3 AI 行动    | 结构化意图解析、校验、判定、叙事 | AI 故障不破坏数据            |
| S4 NPC 记忆   | 人物状态、关系、记忆与任务关联   | 后续反应能引用已保存事实     |
| S5 动态江湖   | 地点、势力、事件传播和 NPC 计划  | 事件影响后续世界状态         |
| S6 发布审计   | 安全、性能、备份恢复和部署       | P0/P1 清零，发布门槛通过     |

# 8. 治理与变更

- 每项功能先定义验收标准，再实现代码。

- 数据库结构变化必须提供迁移文件与回滚/恢复考虑。

- 核心规则变更必须更新测试、技术说明书和相关审计项。

- 未经评审不得引入新的框架、服务或大范围重构。

- 任何未解决的 P0/P1 问题均阻止阶段验收与发布。

# 9. 主要风险

| **风险**          | **影响**           | **缓解措施**                               |
|-------------------|--------------------|--------------------------------------------|
| AI 叙事与事实冲突 | 世界可信度下降     | 程序状态为权威；AI 仅叙述已确认结果        |
| 调用成本过高      | 运行成本不可控     | 普通结算不调用模型；限流、缓存、上下文裁剪 |
| 状态重复提交      | 资源复制或重复事件 | 幂等键、事务和行动状态机                   |
| NPC 记忆膨胀      | 成本升高、事实冲突 | 结构化记忆、摘要、检索和过期策略           |
| 范围膨胀          | 无法按期交付       | 严格限制首期范围，逐阶段验收               |

# 10. 项目完成定义

- 核心循环完整且可以在浏览器游玩。

- 自由行动经过服务端规则验证后才影响游戏状态。

- 在线、离线、存档与 NPC 状态在刷新和重登后保持一致。

- 核心自动化测试通过，P0/P1 缺陷为零。

- 具备部署说明、备份恢复步骤、审计报告和后续开发文档。
